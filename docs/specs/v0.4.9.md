## Items

1. **Naps and bedtime pending.** Found by the Home Assistant chat while reviewing the 0.4.8
   blueprint edit: the integration's automatic report "in bed 10 minutes with bedtime pending and
   no RUN_BEDTIME" doesn't check for a nap, so a nap taken while tomorrow's alarms are set files a
   false report.
   - **The blueprint now handles naps (read 31 Oct, read-only):** `automation.bedtime_nudge` uses
     **Bedtime Nudge v1-05** (`bedtime_nudge_v1-05.yaml`). Since v1-03/v1-04:
     - **Bedtime pending** passes the window check at any hour but only earns the **tap-to-run**
       push, never the auto-run (Michael's call: a lie-down with the door shut would otherwise
       sweep the house, maybe with Seth downstairs).
     - **The auto-run window** runs from its usual start to **2 h before the first alarm**, read
       from the next-alarm sensor's `alarm_times`, within 14 h of the start. That would have
       auto-run the 31 Oct 4:01 bedtime.
     - **Naps:** while `input_boolean.napping` is on, nothing is sent at any hour, checked before
       the warning and again before the push; it only blocks for 4 h after it turned on, in case
       "nap ended" is lost. Bedtime Bridge turns it on when a nap is set at home and off when the
       nap ends.
     - **One bedtime per night (v1-05):** once the routine has run, nothing more is sent before
       the cut-off.
     - **The nap ending isn't a trigger:** staying in bed after the nap alarm sends nothing until
       you get back into bed or the door closes.
   - So `bedtime_pending` itself doesn't need to change for naps (the earlier proposal to pause it
     during a nap is dropped). What's left here:
   - **Fix (integration):** the automatic report skips naps, the same way the blueprint does: no
     report while a nap is on (nap alarms set, or the napping helper on for less than 4 h). It
     already expects one report on a tap-to-run night that's never tapped (correct: bedtime didn't
     run).
   - **The nap that turns into the night** (Michael's case: you nap, don't get up, and it's
     bedtime): **decided 31 Oct, the blueprint handles it** (a hand-off to the Home Assistant
     chat, not built here): the napping helper turning off becomes a trigger that runs the
     blueprint's usual checks; inside tonight's window it auto-runs, outside it with bedtime
     pending it's the tap-to-run push. Nothing in Bedtime Bridge changes for this part.

2. **The 0.4.8 hand-off gave the wrong entity id for bedtime pending.** The blueprint's notes:
   the sensor is `binary_sensor.master_bedroom_bedtime_bridge_bedtime_pending`, not
   `binary_sensor.bedtime_bridge_bedtime_pending`, because the Bedtime Bridge device was moved to
   the Master Bedroom area before 0.4.8 added it, and Home Assistant prefixes new entity ids with
   the area. The blueprint uses the right id; the hand-off would have pointed at nothing.
   - **Fix:** correct `docs/ha-handoffs-v0.4.8.md` (and the README) to say "read the id back"
     with the real one as the example; and from now on hand-offs name an entity by what it is
     ("Bedtime Bridge → Bedtime pending") plus the id as read from Home Assistant, not the id
     the integration would pick on a fresh install.
   - The section 2 blueprint edits in that hand-off are superseded by v1-05; say so there.

3. **The Lock Screen widget doesn't show a nap.** Testing 31 Oct with tomorrow's alarms set and a
   nap on: the Lock Screen showed the morning's alarms, not the nap.
   - **Cause (read-only):** the widget reads the app's alarm snapshot, which holds the regular
     alarms and temporary alarms but not nap alarms (`NextAlarmSnapshot`: `alarmTimes` and
     `temporaryAlarms`, no naps). So "next alarm" skips the nap, in every size (Lock Screen
     rectangular, circular and inline, and the Home Screen sizes), and the medium/large timeline
     doesn't list it either. Only the app's bar shows "Napping · up at …".
   - **Fix:** the snapshot carries the nap's alarms, and while a nap is on the widget leads with
     it: **"Nap · up at 3:20"** (rectangular and small), "3:20" with a nap icon (circular), "Nap
     up 3:20" (inline), with the morning's first alarm under it where there's room ("Then 5:00
     tomorrow"). The timeline lists the nap alarms first. It goes back to the morning once the
     nap ends. Snoozing a nap shows "Snoozing · rings 3:29" as it does for the morning.
   - **A nap Live Activity too (decided 31 Oct):** from setting the nap until it ends, the Lock
     Screen and Dynamic Island show **"Napping · up at 3:20"** with a countdown to the first nap
     alarm and **End nap** (which opens the app's slide-and-hold, as End nap does in the bar).
     Snoozed: "Snoozing · rings 3:29". It ends when the nap does (last nap alarm stopped, End nap,
     or Change nap sets a new one, which updates it). Started by the app (home or away); no Home
     Assistant push needed, since the nap is set on the phone.

4. **Stopping a nap alarm from the banner ran the morning and cleared tomorrow's alarms.**
   31 Oct: own alarms set for 5:00 tomorrow (15:59), nap set at 16:00. At 16:31 Michael stopped a
   nap alarm and Home Assistant sent RUN_GOOD_MORNING.
   - **What happened (read-only, Home Assistant's logbook and Last event):** the app sent
     `stopped` for a regular alarm, not a nap: `last_stop` says `up: true`, `stop_behavior:
     keepUntilUp`, `alarms_left: 0`. Being up, the app ended "the rest of the series", which took
     **tomorrow's 5:00 alarms** with it (Next alarm went to unknown, cause `noalarm`, bedtime
     pending off). Home Assistant then ran the stop routine and sent RUN_GOOD_MORNING; Good
     Morning answered *Already done*, so the house wasn't woken again. The nap's second alarm
     stayed set (the stop leaves "kept" alarms alone, and it was still scheduled), so the app
     still counted the nap as on; *Nap ended* was never sent, and the napping helper stayed on.
     Stopping that second alarm from the banner would have gone the same way (another `stopped`).
   - **Cause (read-only, in the app):** the app decides "is this a nap (or temporary) alarm?" from
     its saved nap and temporary alarms, **filtered to the ones AlarmKit still has**. Stop on the
     banner or Lock Screen is the system's: AlarmKit removes the alarm *before* the app's Stop
     action runs, so by then the nap alarm is no longer in the list, and it's taken for a regular
     alarm. In the app's own Stop screen the alarm is still there, which is why it hadn't shown
     up before. It affects temporary alarms the same way, and it was there before 0.4.8; 0.4.8's
     banner Stop (item 4) asks the same question, so a nap stopped from the banner while still in
     bed would have been snoozed as a regular alarm instead.
   - **Fix:** the Stop (and Snooze) actions decide what kind of alarm it is from the saved nap,
     temporary and test alarms as they were set, not only the ones still scheduled; and the
     alarm itself says what it is (its cause, `nap` or `temporary`, is already in its metadata),
     as a second check. A nap alarm stopped from anywhere: the nap path (the other nap alarm stays
     as a backup; *Nap ended* once none is left), never the morning's. A temporary alarm: the
     temporary path. Nothing about tomorrow's alarms, backstops or Good Morning changes.
   - **And a guard:** stopping any alarm never cancels alarms of a *later* wake-up (another day,
     or more than a few hours after the one ringing); "the rest" means this wake-up's series only.
   - Tests: stop a nap alarm, a temporary alarm and a regular alarm by the banner path (alarm
     already gone from AlarmKit), each with tomorrow's alarms set; tomorrow's stay.

5. **"✓ 3 alarms set" with all three alarms off.** After item 4's stop (31 Oct), Tonight shows
   tomorrow's three alarm bubbles as off, but the header still says "✓ 3 alarms set".
   - **Cause (read-only):** the header above the bubbles (`AlarmBubble.header`) counts every
     alarm "set this morning", ringing, snoozing or **off**, so it holds through a morning after
     the alarms have rung. A stop marks the wake-up as stopped, and then alarms that were
     cancelled before their time also show as off and still count.
   - **Fix:** the header counts what's still set plus what has actually rung. When the rest were
     cancelled before ringing, it says so: **"Alarms off"** (none set any more), "Ended early"
     after *I'm up early*, "1 of 3 alarms left" when some are still to come. No green check
     unless something is still set or this morning's alarms really rang. (Item 4's fix stops this
     case happening, but the header should be right whatever turns them off.)

6. **"Backstops armed" and "First day back" on a day off.** Saturday 31 Oct, own alarms for
   Sunday without backstops: Your morning says *Backstops armed* and *First day back*.
   - **Cause (read-only):** Home Assistant's ladder is armed for the **next shift on the
     calendar**, Monday 2 Nov 6:30 (`sensor.master_bedroom_bedtime_bridge_ladder_status`:
     `armed`, `morning: 2026-11-02T06:30`), and it's Monday that's the first day back. The app
     shows the ladder's status and times on whatever morning it's showing, without checking that
     the ladder is for that morning.
   - **Fix:** Your morning shows backstops only when the ladder is for **that** morning (its
     `morning` on the same day as the alarms shown). Otherwise: your own alarms' backstops if
     you turned them on, or one quiet line, "No backstops Sunday · armed for Monday 6:30", and no
     First day back. The same check for the widget and the Live Activity's "next backstop".

7. **Daylight saving time.** Checked read-only on 31 Oct, the night clocks go back (1 Nov, 2:00 →
   1:00). Alarms are set for a clock time on the day, Home Assistant's timers all run in UTC, its
   time zone is America/New_York, and the ladder's Monday 6:30 is stored as `-05:00`, so
   **tonight is fine**. Three spots treat a day as 24 hours, which goes wrong when the clocks go
   **forward** (14 Mar 2027, a 23-hour day):
   - **"Tomorrow" as now + 24 hours** (`BedtimeCoordinator.swift:168`, the away summary's wake
     day; `ContentView.swift:366`, the backstops default for a leave day; `WindDownSettings.swift:90`):
     between 11 PM and midnight on Saturday 13 Mar it lands on **Monday**. Use
     `Calendar.date(byAdding: .day, value: 1, …)`.
   - **A day as start of day + 86,400 s** (`Vacations.swift:115`): on 14 Mar the range runs into
     the next day, so Monday's vacation counts for Sunday; on 1 Nov it stops at 11 PM. Use the
     next day's start of day.
   - **Curtains open at sunrise on another day** (`bridge.py` `_curtains_open`): it moves
     Home Assistant's next sunrise by whole days in UTC, so across a change it's an hour out.
     Move it by days in local time.
   - **Test:** each of these on 13–14 Mar 2027 and 31 Oct–1 Nov 2026 in America/New_York, plus a
     5:00 alarm planned the evening before each change.
