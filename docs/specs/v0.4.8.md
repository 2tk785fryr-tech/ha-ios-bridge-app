# Bedtime Bridge v0.4.8

Started 31 Oct 2026. App and integration (0.4.8; 0.4.7 is the last released integration).
Draft: items get added here, and nothing is built until Michael says to build.

## Rules (as for v0.4.7)

- Pull first; work on `claude/ios-home-assistant-app-73ao17`; commit in small steps and push;
  Michael merges from GitHub.
- Build exactly what the list says; if something can't work as written, stop and ask.
- Bump `custom_components/bedtime_bridge/manifest.json` to 0.4.8 if the integration changes. A
  test for every item (pytest `tests/ha`, `BedtimeBridgeTests`); run both, and build and run on
  the iPhone before an item is done.
- Don't change the live Home Assistant: HA-side changes go in `docs/ha-handoffs-v0.4.8.md`, phone
  shortcuts in `docs/shortcuts.md` (signed shortcut files stay out of git; copies to install go
  in Desktop → Shortcuts → to import → <date>). Update `docs/setup.md` with any new step, and the
  README (and its pictures) where a screen changes.
- Protected actions use the bottom-bar slide-and-hold.

## Items

1. **Bedtime didn't start after setting your own alarms late (30–31 Oct).** Home late, alarms set
   in the app downstairs at 3:52 AM (own time, 10:00 AM; Sleep In went on, correctly). In bed at
   4:01, but the bedtime nudge never sent RUN_BEDTIME, so the lights stayed on.
   - **Cause (read-only, Bedtime Nudge trace 04:04 AM):** your Bedtime Nudge blueprint
     (`bedtime_nudge_v1-02.yaml`) only nudges inside a clock window: with no shift it's the off-day
     window, 21:00–04:00. In bed at 4:01, the 3-minute dwell ended at 4:04, outside the window, so
     it stopped at "Inside the widest bedtime window: false". Nothing in Bedtime Bridge was involved.
   - **Fix (decided 31 Oct: the new sensor):** when Bedtime Bridge has alarms set for later and
     bedtime hasn't run since they were set, getting into bed is bedtime at any hour, until 2 h
     before the first alarm. The integration adds `binary_sensor.bedtime_bridge_bedtime_pending`
     (on from a plan or own alarms until bedtime runs or that cut-off), and the blueprint nudges when
     it's on, even outside its window. The blueprint change is a hand-off (it's your blueprint in
     Home Assistant, not in this repo): an extra "or bedtime pending is on" next to the window
     check. The window itself stays as it is.

2. **The bedtime shortcut asked for a wake-up time although your own alarms were set, and cleared
   them.** When you ran the bedtime shortcut by hand, it asked "what time do you want to get up?";
   you cancelled, ran it again and picked the same time, which set the alarms again.
   - **Cause (read-only):** the shortcut's first step, *Plan Wake-Up Alarms*, plans from the
     calendar. On a day off it finds no shift or event, so it returns *Has Alarm: false* and, with
     *Set Alarms* on, clears the app's alarms (as it's meant to for a "no alarm" night). Your own
     alarms from *Set alarms for a time* went with them, and the shortcut then asked the day-off
     question.
   - **Fix (decided 31 Oct: keep your alarms, and confirm them):** when your own alarms are set for
     the coming morning, *Plan Wake-Up Alarms* keeps them, even if it finds a shift or event, and
     asks once: "Keep your alarms at 9:40, 9:50 and 10:00?" with **Keep**, **Change time** (asks for
     the first alarm, as *Set Wake-Up Alarms* does) and **No alarms** (the day-off question,
     Sleep In). If it found a shift or event that needs an earlier wake-up, the question says so:
     "Your shift needs you up at 5:30. Keep your alarms at 10:00?" Run from Home Assistant's
     push with nobody to answer, it keeps them.
   - It returns the alarms it kept (*Has Alarm: true*, the times, "Your own time"), so the
     shortcut's `Alarmtimes` holds them and the **Bedtime Readout** announces them on the iPhone
     and the speaker ("Alarms at 9:40, 9:50 and 10:00"), as it does for a planned morning. Nothing
     changes in the shortcut for that; to check in the readout's wording that "Your own time"
     reads well.

3. **The 2 hours before the alarms: End alarms belongs in the bar, with Sleep later.** In the up-early
   window (2 h before the first alarm) the *End this morning's alarms* card was on the main screen;
   it should move into the bottom bar, which should also offer *Sleep later*.
   - The bar is meant to show "1 alarm set · first at 10:00" with *I'm up early* and *Sleep later*
     in that window; the card shows as well. Michael remembers the bar's main choice as something
     like *Set alarms* with *Preview plan* (not a cancel).
   - **Likely cause (read-only, not proven):** the bar checks "plan changed" before the up-early
     window. With your own alarms set and a calendar plan of "no alarm" for that morning, the app
     treats the set alarms as out of date (`PrimaryAction`: *Plan changed: update alarms* or *Set
     the missing alarms*), so the bar shows the re-plan prompt (*Re-plan* / *Update alarms*, with
     *Preview plan*) instead of *I'm up early* / *Sleep later*. Tapping it would have re-planned
     from the calendar and cleared your alarms, the same trap as item 2.
   - **Fix:** your own alarms are never "out of date" against the calendar (they aren't from it);
     only a plan's alarms are. And in the up-early window, that window's bar wins over a re-plan
     prompt. The card leaves the screen; the bar is the one place: *I'm up early* (slide-and-hold)
     and *Sleep later* (and *No alarms this morning*, item 7). A test reproduces last night: own
     alarms at 10:00, no shift, 8:30 AM.

4. **Ending an alarm from the banner is too easy.** Using the phone when the alarm went off, it
   showed as a banner with *Snooze* and *Stop*; one tap on Stop ended it and Good Morning ran.
   - **What's possible (AlarmKit):** the banner and Lock Screen buttons are the system's: Stop
     always stops, there's no hold-to-stop there. What the app can do:
     a. **Stop from the banner counts as a snooze** unless you're up: the alarm comes back after
        the snooze length unless you end it with the slide-and-hold in the app, or Home Assistant
        sees you're up (bedroom door / bed empty, as *Keep the rest until I'm up* already does).
     b. **The second button opens the app's Stop screen** (slide-and-hold) instead of being a plain
        Snooze; the first stays the system's Stop (with a.).
     c. **Good Morning waits until you're up:** stopping an alarm in bed no longer runs Good Morning
        straight away; it runs once Home Assistant sees you up (or the app's slide-and-hold ends the
        morning).
   - **Decided 31 Oct: a and b.** c is not built (Good Morning still runs when the alarms end the
     usual way, the slide-and-hold or Home Assistant seeing you up).
   - With a: a Stop from the banner is logged as a snooze, the same snooze count and length; the
     Live Activity and the bar show "Snoozing · rings 10:09". Once you're up (bedroom door / bed
     empty) or you end it in the app, the rest go and Good Morning runs as today.

5. **Good night is the bar's main button once alarms are set, with Change plan and Temporary
   alarm.** After setting alarms in the app (planned or your own), the bar is:
   - **Top line:** "✓ 3 alarms set · first 10:00", with **Undo** on it while Undo applies (item 6).
   - **Main button: Good night** (slide-and-hold, since it turns the lights off). It starts the
     bedtime sequence, like *I'm awake* does good morning: it asks Home Assistant to send
     RUN_BEDTIME (the same push the bedtime nudge sends), so *I'm ready for bed - app* runs and the
     house goes to bedtime.
   - **Two buttons under it: Change plan** and **Temporary alarm** (Temporary only with the app's
     own alarms, as now).
   - Once bedtime has run, Good night goes and the bar is as today after bedtime (*Not ready for
     bed* / *Sleep later*); in the 2 hours before the alarms it's item 3's bar.
   - **Change plan** opens one sheet with every way to change tonight's alarms, in this order,
     each hidden when it doesn't apply:
     1. **Undo**: put back what was there before (alarms or none).
     2. **Change times**: move or remove single alarms (today's *Edit alarms*).
     3. **Set alarms for a time**: replace them with your own time (your own alarms' series).
     4. **Plan from the calendar again**: today's *Preview plan*, then *Set alarms*.
     5. **Sleep later**: in its window, as now.
     6. **No alarms tomorrow** (*this morning* after midnight, item 7): ends them and their
        backstops, and asks about Sleep In.
     This replaces the bar's *No alarms tomorrow* and *Edit alarms* buttons. The bar's **⋯** stays
     where it is, with its full list (Nap, Skip, Add a wake-up event, Add vacation, Settings...).
   - The layout is the render Michael approved on 31 Oct (Good night slide-and-hold filling the
     bar; Change plan and Temporary alarm outlined under it; Undo at the right of the top line).
   - **Siri (decided 31 Oct): yes.** "Good night in Bedtime Bridge" (and "Bedtime Bridge good
     night"). Siri can't do a slide-and-hold, so it asks "Start bedtime now? The lights will go
     off." and you say yes. Apple allows an app 10 Siri shortcuts and the app has 10, so one goes:
     proposed, *Cancel wind-down* (still in the app's bar and ⋯, and as an action in the Shortcuts
     app; only its spoken phrase goes). To confirm when building.
   - A Control Center control too? Not asked for; left out unless Michael says.

6. **Undo after Set alarms for a time.** Undo (v0.4.3 item 2) only appears after a *Preview →
   Set alarms*. Setting your own time (*Set alarms for a time*) keeps nothing to undo, so there's no
   Undo afterwards (checked, read-only: `scheduleManual` saves no undo record). Fix: it keeps what
   was there before (alarms or none), and Undo shows on the bar's top line ("3 alarms set · Undo")
   and first in *Change plan* (item 5), as after a preview, until bedtime runs. Every change made
   from *Change plan* can be undone the same way (one step back).

7. **Changing your mind in the night: no alarms, with or without Sleep In.** Woken in the night after
   setting alarms, decide to sleep in with no alarms: one action ends them (and any backstops they
   had) and asks about Sleep In.
   - **What's there now (read-only):** with alarms set, the bar offers *No alarms tomorrow* (it asks
     Sleep In on or off; the backstops go off unless a shift is still on the calendar that morning).
     From 2 h before the first alarm it's *Change this morning* in ⋯ instead (turn this morning's
     alarms off, with a reason). After midnight it still says "tomorrow", which reads wrong.
   - **Fix:** after midnight (or once it's the alarms' own day) it reads **No alarms this morning**,
     and it stays in the bar, with Sleep In, up to the first alarm, including the 2-hour window
     (next to *I'm up early* / *Sleep later*, or in ⋯ there). Your own alarms' backstops (if you
     turned them on) go off with them.

8. **Settings → "Shortcuts, controls and Siri", with a page of everything you can say.** The
   *Shortcuts & controls* row is renamed **Shortcuts, controls and Siri**. At the top of that page,
   a new row **Siri phrases** opens a page listing every phrase the app answers to, grouped by what
   it does (alarms, bedtime, morning, nap, wind-down, calendar), each with what it does in one line
   ("Good night in Bedtime Bridge: starts bedtime, after you confirm").
   - **Changing what you say:** Apple doesn't let an app's own phrases be changed, by the user or
     the app; they're fixed in the app and always include "Bedtime Bridge". What does work: make a
     shortcut in the Shortcuts app with the name you want to say ("Let's go sleepy bye") whose one
     step is Bedtime Bridge's **Good night** action; Siri runs a shortcut when you say its name.
     The page says so, with an **Add your own phrase** button that opens the Shortcuts app, and the
     steps in `docs/shortcuts.md`. Names to avoid: anything close to an existing shortcut's name
     (e.g. *I'm ready for bed* vs *I'm Ready For Bed - App*), or Siri may ask which one you meant.

9. **Report something, for the testing phase.** A way to note "that just went wrong" in the moment,
   that Claude can then read without you retelling it.
   - **Where:** **Report something** at the top of ⋯, and a Control Center control (so it works
     from the Lock Screen or the Action button). On while *Settings → About → Testing reports* is
     on (on by default for now).
   - **What it saves:** what you type or dictate (can be empty), the time, and a snapshot the app
     fills in: the bar's text and buttons as shown, the main screen's cards, the alarms set (times,
     own or planned, backstops), the plan, which window it's in (bedtime, up-early, snoozing...),
     Sleep In, the last messages to and from Home Assistant, and what the app did in the last 12 h
     (a short activity log the app starts keeping for this, no personal data beyond the alarms and
     calendar titles it already uses). Optionally a screenshot of the app as it was.
   - **How Claude reads it:** the app sends it to the Bedtime Bridge integration (the existing
     webhook), which appends it to a reports file in Home Assistant's config folder and writes one
     line to the log ("Bedtime Bridge report: <first words>"). Claude reads that file with the Home
     Assistant tools in the next session ("read my reports") and turns each into a spec item. A
     copy stays on the phone (*Settings → About → Testing reports* lists them, with Share) for when
     Home Assistant can't be reached; it sends them later.
   - **Where the file goes (checked 31 Oct):** the Home Assistant tools here can only read `www`,
     `themes`, `custom_templates`, `dashboards`, `blueprints`, `packages`, `templates` and
     `scripts`. `www` is out: anything in it is served at `/local/` without signing in, and the
     reports hold calendar titles and alarm times. So the integration writes to its own folder,
     `bedtime_bridge_reports/` in the config folder (`reports.jsonl`, one report per line, the
     last 200 kept), and Michael adds that folder in the ha-mcp settings (custom directories) so
     Claude can read it. Screenshots go next to it as `<time>.png`.

10. **Integration settings: back to the menu after a page.** Today *Configure* opens the menu
    (v0.4.7 item 9), but submitting a page saves and closes the whole dialog, and there's no way
    back to the menu from a page; you have to close or submit and open *Configure* again.
    (Checked: each page ends with `async_create_entry`, which ends the flow.)
    - **Fix:** submitting a page keeps its changes and goes **back to the menu**. The menu gets a
      last option, **Save and close**, which saves every page you changed at once. The menu's text
      says which pages have unsaved changes ("Changed: Wake-up, Phone").
    - Leaving a page without changing anything: submit it as it is, and you're back at the menu.
      Home Assistant's forms have no Back button of their own (that may change with 2026.11; if it
      adds one, use it).
    - Closing with ✕ before *Save and close* drops the changes; the menu text says so.
